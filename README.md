## 1. Какой принцип SOLID применен наиболее явно и где?
1. Наиболее явно применены принципы Single Responsibility:
	- Это выражено в блоке с ServiceCenter и BeginnerPolicy. Изначально я думал сделать проверку на то, подходит ли транспорт новичку в блоке сервиса, проверяющего работоспособность транспорта.
	- Адаптеры для ввода и вывода данных в программу отвечают соответственно только за вывод и за считывание данных, все данные приходят в них из KickSharing.
2. Dependency Inversion Principle:
	- Во всем проекте был акцент поставлен на то, чтобы все элементы по-максимуму зависели не от конкретных реализаций, а от интерфейсов и абстракций(Примеры: IKickSharing, IInventoryObject, IEnergyConsumer...). Есть одно место, где это осознано нарушено, чтобы не перегружать учебный проект.
3. Open-close:
	 - Если появятся новые виды транспорта, то нужно будет только дописать новый класс транспорта или предмета в модуле Vehicles или Things. При этом не нужно будет переписывать логику оценки транспорта и самого паркинга.

## 2. Какой принцип сознательно ограничен/нарушен и почему это приемлемо?
Сознательно были допущены ограничения в блоке консольного UI. Во-первых, частично нарушен **DIP**: в меню напрямую вызываются конструкторы конкретных видов транспорта (например, `new Bike()`), минуя абстрактные фабрики. Во-вторых, нарушен **OCP**: при добавлении нового транспорта придется модифицировать код меню, добавляя новые пункты в жестко заданный `switch-case`. Я считаю это приемлемым, так как внедрение паттернов Factory и Command для избежания этих нарушений привело бы к overengineering'у и сильно усложнило бы читаемость простой консольной программы. UI — это самый изменчивый слой, и такая прямолинейность здесь оправдана.

## 3. Что сломается (или не сломается) при добавлении нового вида транспорта, сотрудника или склада запчастей (можете придумать свой вариант расширения программы)

Так как Кикшейринг сделан с соблюдением DIP, то при добавлении нового вида транспорта придется менять только UI ввод данных, чтобы добавить туда новый вариант выбора. В остальном нужно будет добавить новый класс транспорта и все будет работать также, как раньше.

При добавлении сотрудников придется переписать логику нашего паркинга, потому что он хранит в себе только списки транспортов и вещей и общий расход с кол-вом инвентаря. Можно или создать новые список для сотрудников или отдельный сервис для учета сотрудников(чтобы не переписывать логику работы паркинга).

При добавлении складов помимо проблем, которые были описаны в предыдущем блоке пришлось бы закрыть для паркинга знания о том, какие у него есть вещи в инвентаре и дать ему знание о складах, а уже в них хранить конкретные вещи. Пришлось бы переделать логику паркинга для того, чтобы склады выполняли свою основную функцию и инкапсулировать элементы инвентаря от прямого доступа из паркинга.

## 4. Какой тест фиксирует решение техосмотра и/или правило «для новичков»; как подменяется зависимость;

Если под "фиксирует решение тех осмотра или правило для новичков" понимается тест, где у нас происходит создание моковских объектов для наших сервисов, то это происходит в следующих тестах:
- Add_VehiclePassesServiceCheck_AddedSuccessfully
- Add_VehicleFailsServiceCheck_NotAdded
- GetBeginnerVehicles_FiltersCorrectly_BasedOnPolicy

Я использовал класс Mock из библиотеки Moq. У него есть метод Setup который позволяет задать функции конкретный результат.

Если же под "фиксирует решение тех осмотра или правило для новичков" понимается просто тест сервиса и правил для новичков, то это происходит в модуле PoliciesAndServicesTests

## 5. Что сделал ИИ, а что изменили вы (если ИИ не использовался — укажите это).
ИИ выступал в роли ментора на этом проекте, чтобы помогать в моментах, где я заходил в тупик при проектировании архитектуры. Также он помогал с тем, чтобы разобраться в синтаксисе C# и библиотеки Moq. С ним был написан блок UI консольного взаимодействия с пользователем, но блок с настройкой DI-контейнера им не затрагивался, там все было сделано мной. 
Также ИИ участвовал в написании тестов, чтобы не тратить время на написание однотипных тестов для разных классов по типу Bike и ElectricBike.
